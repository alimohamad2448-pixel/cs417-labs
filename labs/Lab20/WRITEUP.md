1. When the client times out, it does not mean the server failed. It only means the client stopped waiting for a response. The server is still processing the request in the background and will usually complete it. What’s happening is that the client sends a request, the server begins working, but the client gives up before the server finishes. This is why retries can lead to duplicate work, because the server may still be completing previous requests while new ones are sent.

2. If the idempotency key were a random UUID generated on each retry, it would not prevent duplicate grading. Each retry would look like a completely new request to the server, so the server would perform the work again every time. Using a key like f"{student}-lab{lab}" works instead. This key allows the server to recognize repeated requests and return the same result instead of recomputing it.

3. Synchronous APIs are appropriate when the result can be returned quickly and the client can reasonably wait. Asynchronous APIs are better when the operation takes longer, since they allow the server to acknowledge the request immediately and let the client check back later. With this in mind, the deciding factor would be how long each of them take respectively. The CoinGecko API returned results quickly so a synchronous approach worked, while the grading system could take several seconds, making an asynchronous approach with polling more appropriate.

4. The hidden state in this lab would be the server continuing to process requests even after the client timed out. At first the client had no visibility into this and it appeared as if requests were failing or needed to be retried. This became visible once we added the grading log, which showed that multiple grading operations were happening due to retries. The introduction of asynchronous endpoints, job IDs, and polling made the server’s internal state visible by allowing the client to check whether a job was still pending or completed.
